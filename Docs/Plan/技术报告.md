## 2. 视觉层如何用 VFX Graph 实现

下表是从图像反推的**可实现方案**，不是原图生成算法的鉴定。核心原则：每层保留固定身份/随机种子；在同一图或固定的几张图内改变暴露参数。全曲不靠更换 VFX 资产、重播四段效果或叠加四张图片来完成。

| 视觉层 | 推荐 Graph 结构与素材 | HLSL / 音乐控制 | 难点与取舍 |
|---|---|---|---|
| 柔光雾、两处光 | Spawn → Initialize Particle → Update Particle → Output Particle Quad（Unlit）。少量拉长软边雾片，低频噪声 alpha，独立 A/B 发光中心；先 Premultiplied/Alpha，少量亮芯可 Additive | 沿两组流线布置，缓慢变形；控制中心、尺度、alpha、发光强度 | 亮雾是有空洞的薄光，不是实体烟团；叠太多会灰白一片，透明排序和 overdraw 比“粒子数量”更危险。URP 不采用 HDRP 专属体积雾输出 |
| 光纤丝带 | Initialize Particle Strip → Update Particle → Output ParticleStrip Quad（Unlit），稳定 strip ID 和沿带索引；窄芯渐隐贴图 | HLSL 求多条相关曲线与切线，控制弯曲、宽度、相位和轻微扰动 | 不是一根很宽的亮 ribbon；要多根窄丝和疏密差。控制条带索引/接缝，避免粒子重生时跨屏连线；容量与每条段数先固定 |
| 星尘 | Output Particle Quad，小圆点/软点贴图，近景少量较锐，远景较软 | 与丝带共用形态场；RMS/高频只改变少量大小和明亮点比例 | 图中的几千亮点不能反推真实粒子数；手机上 1 像素以下可能闪烁，随分辨率下限调节 |
| 光斑 | 少量较大朝向相机 Quad，预模糊光盘贴图；独立低亮度输出 | 位于近远层，慢漂移；轻微 RMS 呼吸 | 光斑不是把所有星尘放大。大 Quad 即使 alpha 很低仍可能消耗填充；不全屏泛白 |
| 花形聚散 | 独立固定粒子池；简单瓣弧目标场 + 微点 + 少量软瓣片，仍由 VFX Graph 输出；C1/C3 成形，C2/C4 只留短弧 | HLSL 按稳定 ID 在“沿流散点”和“有断口瓣弧目标”间连续混合；歌词包络控制聚合；残余噪声始终存在 | 一朵局部记忆，不画完整花束/茎叶。C1/C3 右上到 C2/C4 左侧不能直线横穿：先散开，低可见度时搬移目标，再聚合 |
| 斜雨 | 定向、拉长 Quad；Orient Fixed Axis 或由速度方向定朝向；长条渐隐贴图 | C2 的雨强由章节启用，onset/节拍只小幅调制；屏幕右下方向的慢连续穿过是运动推测 | 静态只能确定斜线方向，不能确定下落方向/速度；其余三帧不强加明确雨层。线段要细、暗、少，允许穿过黑隙但不能填满 |
| 黑隙 | 无独立“黑粒子”；共享局部排斥/透明度衰减场，作用于雾、丝带、星尘和花；C2 雨层使用较弱避让 | HLSL 在目标场与输出 alpha 做软边抑制；章节控制位置/宽度，节拍不关闭此约束 | 输出黑色在 Additive 中不会变黑。C3 测得局部缝宽约 0.0063W（11 px/1672），Bloom 会跨缝；不能靠 alpha mask 就保证后处理后仍黑 |
| 景深虚实 | 先以深度分组 + 软硬贴图混合 + 尺度差模拟虚实；真 DOF 为可选实验 | `FocusDepth / DepthSpread / SoftFraction` 只给“虚实代理”，不声称等于相机真实焦距 | 透明粒子默认不写深度；仅开启 DOF 不保证对每一透明层按正确深度虚化；Soft Particle 是交界软化，不是 DOF |

上述节点类型、混合与深度行为参见 [VFX 输出设置](https://docs.unity3d.com/Packages/com.unity.visualeffectgraph@17.3/manual/Context-OutputSharedSettings.html)。条带结构此前已对照17.3包内 `Documentation~/Context-OutputStripQuad.md`；该包文档将条带定义为连续Quad带。实际菜单措辞以新工程所装17.3为准，不依赖旧工程缓存路径。具体数量、尺寸、深度及逐帧差异见 [风格帧拆解](风格帧拆解.md)。

### HLSL 能减少节点，但不能替代整张图

建议以后只编写几个可解释的 HLSL 功能：流线位置/切线、花形目标、局部黑隙遮罩、细节扰动。Custom HLSL Block 可在 Init/Update/Output 处理粒子属性；Operator 适合无副作用计算。外部文件可复用；Operator 有最多 4 个函数参数等签名限制。纹理采样须适配 compute/vertex 上下文，不能使用片元导数 `ddx/ddy`。渐隐贴图和片元外观仍由 Output/必要的 Shader Graph 负责，容量、Spawn 与连接仍需手动搭图。[Custom Block](https://docs.unity.cn/Packages/com.unity.visualeffectgraph@17.3/manual/Block-CustomHLSL.html)、[Custom Operator](https://docs.unity.cn/Packages/com.unity.visualeffectgraph@17.3/manual/Operator-CustomHLSL.html)、[共同限制](https://docs.unity3d.com/Packages/com.unity.visualeffectgraph@17.3/manual/CustomHLSL-Common.html)

## 3. 为什么选择 Unity，而不是另外两条路线

| 判断维度 | Unity VFX Graph（推荐） | Unity 内置 Particle System + C# | Three.js |
|---|---|---|---|
| 雾 / 星尘 / 雨 / 光斑 | GPU 粒子和可复用图层，适合本任务 | 模块容易上手，同样可以做；粒子量和脚本更新成本需测 | Points/实例化 Quad/自定义 shader 可以做，不能说视觉上做不到 |
| 细丝与花形目标 | 条带 + GPU 属性/自定义 HLSL，图内统一 | Trails/自定义粒子位置可做；复杂有序丝束需要较多定制 | 需要自己组织曲线/实例数据/模拟、shader 和调试工具 |
| 音频 / 编排 | C# 时钟与图参数分工清楚 | C# 可以直接访问粒子，改起来直观 | Web Audio/AudioAnalyser 可接频谱；状态与歌词编排仍要单独写 |
| 编辑器与未来终端 | 先在Windows编辑器完整验收；未来iPhone走Metal/ARKit，另做真机测量 | 平台覆盖较广，仍要验证；不符合本次硬性选型 | 浏览器和WebGPU/WebGL能力、未来AR/设备接入要另验证；不能等同于原生AR Foundation |
| 本次取舍 | 用户要学手搭图，助手能补 HLSL；与后续终端、工作流一致 | 作为技术比较，不能偷偷用它替代指定 VFX 粒子 | 适合快速预览与沟通；不作为这次正式实现路线 |

本任务选择Unity，是为了用户可手搭的VFX图、编辑器调试和未来原生AR工作流。Unity官方区分VFX的GPU模拟与内置系统更直接的C#粒子访问；三者均能做出相近视觉，实际取决于实现与调试。[Unity 粒子系统选择](https://docs.unity.com/en-us/engine/6000.3/manual/visual-effects/particle-systems/choosing-your-particle-system)、[Three Points](https://threejs.org/docs/pages/Points.html)、[AudioAnalyser](https://threejs.org/docs/pages/AudioAnalyser.html)、[WebGPURenderer](https://threejs.org/docs/pages/WebGPURenderer.html)。WebGL回退不代表所有WebGPU compute代码自动等价。

## 4. 三个时间尺度如何同时驱动

系统每帧产生同一个“最终参数包”。组合次序：**章节基态 → 歌词偏移与有限音频微扰 → 锚点调制权重 → 黑隙与亮度限幅 → 参数输出**。M1显示和记录最终参数；M2以后再接Graph。

| 时间尺度 | 信号来源 | 控制哪些东西 | 明确不做什么 |
|---|---|---|---|
| 慢：数秒到一章 | `chapters`、四个关键状态、少量入口/出口辅助状态 | 两光位置/尺度、流线弯曲、主色、雨层权重、留白、整体密度、虚实 | 不等到章节边界才硬换图，也不靠 FFT 猜下一章 |
| 中：一句歌词 | `lyric_units` 起止、成形标注、意象转述；句间窗口 | 花形/局部尘点的聚拢—短暂可辨—散开；灯光团的局部密度 | “成形”不等于每句都长出花。需在视觉编排侧将句意映射到 M1/M2/M3，保留源时间线 |
| 快：几十毫秒到一拍 | 实时 RMS / low / high；校准 beat 列与 onset 候选 | 丝宽 ±约 8%、亮度 ±约 15%、噪声幅度、稀疏亮点脉冲 | 不让低音每拍大幅移动两光中心，不让节拍填平黑隙，不把瞬态一律当鼓点 |

具体系数仍为方案初值，见参数合同。RMS/频段实时计算；节拍层级已经确定为 **68 BPM**，从既有约136 BPM的616个beat中每隔一个取一个。实施需比较两种相位的局部声学证据，选择更可能对应强拍的一组并生成本地核对音频；相位选择依据与实测结果放DEVELOPMENT.md。既有985个onset仍是瞬态候选，不能当成downbeat。源 `timeline.json` 没有完整beat时间列，适配时须保留同源时基；68 BPM不是已验证拍号或每小节第一拍的证明。

时钟采用 `AudioSettings.dspTime` + `AudioSource.PlayScheduled`，音频缓冲准备好才统一开始；暂停、seek、恢复显式维护起点偏移，不能假定暂停单个 AudioSource 会冻结整个 DSP 时钟。`GetSpectrumData` 用于视觉调制；它不是歌词识别器或可靠节拍检测器，也不提供严格低延迟保证。FFT bin 要按输出采样率计算。固定曲目的已分析 beat 是同步编排，实时 RMS/频段仍持续影响每一帧；这满足连续音驱视觉，但不把它宣称成任意歌曲的全在线语义分析。[dspTime](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/AudioSettings-dspTime.html)、[PlayScheduled](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/AudioSource.PlayScheduled.html)、[GetSpectrumData](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/AudioSource.GetSpectrumData.html)

### 四张图是经过的关键状态，不是四张停住的画面

关键时刻已固定为 **56.80 / 93.61 / 155.41 / 264.05 秒**，依据及仍待听审的歌词边界见脚手架方案。**M1在精确锚点求值时，最终视觉参数必须等于该帧预设的每个字段。** 不是只让章节基态相等，也不是只允许“接近”。基态轨迹经过四预设；靠近锚点时用连续、平滑的权重将歌词偏移与快层调制减小，到锚点权重为0，离开后再恢复。所有预设名称与四组数值保持不变。

章节边界前后约 4 秒做平滑过渡，内部仍有缓慢发展。四个状态共用粒子身份、条带拓扑和目标场；位置沿流线/控制点过渡，颜色在线性空间混合，角度走连续路径，数量用可见权重过渡。复杂曲线不仅靠几个数字：每章还需一组有限的流线控制点；先手动 2–3 条主路径，别一上来做全流体求解。花形跨屏搬移通过“先散—弱显时移位—再聚”避免穿过黑区。

锚点约束不停止音频或SongTime，不伪造 `Rms01/Low01/High01/BeatPulse/LyricEnvelope` 等原始信号。预设本身的 `NoiseAmp` 仍取原值；归零的是**额外调制权重**。将来粒子仍可按预设速度和累计相位流动，因此“精确参数锚点”并不意味着画面冻结。M1需以精确时刻离线求值和前后连续采样同时验收；不能依赖渲染帧恰好采到该小数秒。后续VFX仍使用暴露属性/事件、不逐章换资产；seek涉及粒子历史，届时另验证重置/预演。[VisualEffect 组件 API](https://docs.unity.cn/Packages/com.unity.visualeffectgraph@17.3/manual/ComponentAPI.html)

### C# 的边界

C#负责音源、DSP时钟、JSON解析、曲线/歌词包络、特征归一化与平滑、关键状态求值、锚点约束、参数校验和调试。M2后HLSL/VFX负责逐粒子位置、稳定随机、形态混合、颜色/大小和输出；C#不生成大量网格顶点来替代指定VFX实现。MCP是编辑器开发工具，不进入歌曲播放的实时链路；未来独立播放器也不依赖MCP服务器。

## 6. 当前三项风险、后续视觉预算与 iPhone 边界

### 6.1 第一风险：参数连续性与锚点精确值相互冲突

只让慢层穿过预设、再直接叠加实时脉冲，会在锚点得到错误的最终值；只在某一帧强制换回预设，又会产生跳变。M1采用平滑的锚点调制权重：基态精确经过四态，句级/快层偏移在附近衰减到0，前后恢复。验收同时检查四时刻全部预设字段的数值误差、相邻时间采样的连续性、整曲范围和暂停/seek行为。阈值与结果以实际测试记录为准；不能把原始音频值覆盖成预设来通过测试。

VFX Graph 17.3仍要求compute shader与SSBO；URP要用Linear，官方仍将URP/mobile列为未结束preview。M2先在当前Windows编辑器验证最小图和着色器编译，再做复杂视觉；未来iPhone的Metal运行必须单独真机证明，不能由编辑器结果推断。[官方要求](https://docs.unity3d.com/Packages/com.unity.visualeffectgraph@17.3/manual/System-Requirements.html)

### 6.2 第二风险：透明覆盖与后处理

以下为 **M2以后待实测的初始视觉预算**，不是从图片数出的真实数量，也不是Unity保证值。当前已确定纯黑背景、30 fps目标；横屏约1280×720内部渲染仍是起步建议。M1没有粒子，不能用M1帧率证明这些预算已经通过。

| 层 | 建议固定容量 | 各章可见预算范围 | 优先优化 |
|---|---:|---:|---|
| 星尘 | 8192 | 2200–6000 个 | 降小点密度；保留主亮群；不每帧分配 |
| 光纤 | 128 strips × 32 samples=4096 粒子采样点 | 64–128 条，32 点/条 | 少条数优先于把单丝变成锯齿；条带还有实际顶点/三角形成本 |
| 花 | 1024 | 280–900 个 | 维持单花、断口和小面积；按状态分配瓣弧/边缘点 |
| 雾 | 64 | 24–48 个大 Quad | 压屏幕面积和重叠；数量少也可能最贵 |
| 光斑 | 64 | 20–40 个 | 限最大尺寸和屏幕叠层 |
| 雨 | 256 | C2 约 120 个，其余锚点 0 | 控制长度/alpha/可见占比 |

固定容量合计约 **13696 个粒子采样槽**；C1 可见目标约 11084，不能将其称为 GPU 内存或绘制顶点数。隐去粒子不一定节省模拟开销；低配档要在启动前选择更低容量，正常章节演出不改容量、不 Reinit。性能定位分别看模拟、strip 几何、透明像素和后处理。

初始后处理：Unlit、无粒子灯光阴影、真 DOF 关闭；Bloom 从低强度开始、关闭高质量过滤；没有用途则关闭 Opaque Texture，需 Soft Particle/深度交互时才开启 Depth Texture。对照 Bloom 开/关及 Render Scale 降低后帧时，确认是否是填充瓶颈；不要先凭感觉增加粒子。URP 的配置优化必须结合 Profiler/Frame Debugger。[URP 性能配置](https://docs.unity3d.com/6000.3/Documentation/Manual/urp/configure-for-better-performance.html)、[移动后处理](https://docs.unity.com/en-us/engine/6000.3/manual/post-processing-and-full-screen-effects/urp/integration-with-post-processing)

后续视觉验收：Windows编辑器完整播完269.747秒，记录机器、输出分辨率、CPU/GPU、P95帧时和卡顿，暂以稳定段P95≤33.3ms为30 fps的检查目标。未来iPhone阶段重新测帧时、内存与持续运行表现，设备能力不够时再降低质量；这些都不属于本轮M1交付。

### 6.3 第三风险：静态参考不等于可验证的连续动效

静态图能测中心、暗部、颜色和局部宽度，不能确认真实粒子数、速度或深度。M2以后每帧预设既要有不带参考图的Unity截图，也要有锚点前后连续片段，证明不是暂停图像或借叠图遮住效果。M1原图对照仅用于检查输入和UI，不能当作粒子成果。

显示形式已确定为 **暗幕方案、纯黑背景**。当前编辑器用纯黑背景忠实对照；未来AR用暗幕承载虚拟画面，明确它会覆盖相应区域的现实。黑隙仍是“没有虚拟发光粒子的间隔”，不能用Additive黑色凭空压暗现实。ARCameraBackground的相机画面和暗幕怎样合成留到AR阶段验证。[AR 相机组件](https://docs.unity3d.com/Packages/com.unity.xr.arfoundation@6.3/manual/features/camera/camera-components.html)

### 6.4 未来 iPhone 的必要条件（仅边界，不在本轮实施）

Unity生成Xcode工程，再由Xcode构建iOS应用；本地完成这一构建需要macOS和Xcode。AR阶段还需Unity的iOS模块、匹配的AR Foundation/Apple ARKit XR Plugin、启用ARKit、相机用途说明和Project Validation通过；实际iPhone型号、系统、Metal与所需AR功能均需真机核验。不在本轮安装、签名、构建或实现AR。[Unity 6.3 iOS构建流程](https://docs.unity3d.com/6000.3/Documentation/Manual/iphone-BuildProcess.html)、[ARKit 6.3配置](https://docs.unity3d.com/Packages/com.unity.xr.arkit@6.3/manual/project-configuration-arkit.html)

Unity6.3官方兼容页列iOS15及以上，推荐Xcode16及以上；Metal支持iOS Player与URP。这里采用Unity6.3的要求，不能把ARKit配置页单列的ARKit平台基线当成完整Unity应用的最低要求；Windows编辑器结果也不能证明Metal真机已通过。[iOS要求](https://docs.unity3d.com/6000.3/Documentation/Manual/ios-requirements-and-compatibility.html)、[Metal兼容性](https://docs.unity3d.com/6000.3/Documentation/Manual/metal-requirements-and-compatibility.html)
